# MXNI instructions for AI agents

This document is the compact behavioral contract for AI systems generating MXNI interfaces, graphics, or implementation code.

## Brand

MXNI is a balanced futuristic technology identity: technical, modular, expressive, and legible.

## Visual constraints

- Default dark background: `#09070D`.
- Surface: `#15111C`.
- Elevated surface: `#211A2B`.
- Primary brand: `#A83FE0`.
- Secondary accent: `#E044C5`.
- Technical/interaction accent: `#24CDE0`.
- Limited highlight: `#B5F52D`.
- Display font: Manrope.
- Technical font: JetBrains Mono.
- Radius scale: 2, 6, 10 px.
- Spacing scale: 4, 8, 12, 16, 24, 32, 48, 64 px.

## Composition

Prefer modular grids, controlled rectangular geometry, clear hierarchy, and negative space. Use subtle technical textures and localized glow. Avoid generic cyberpunk, excessive neon, random circuit patterns, rainbow gradients, and decorative noise.

## Product adaptation

Keep foundations consistent. Adapt density, navigation, semantic colors, and composition to the product's task. Do not force a marketing layout into a functional application.

## Accessibility

Target WCAG 2.2 AA. Use semantic HTML, keyboard navigation, visible focus, reduced motion, accessible labels, and non-color status cues.

## Platforms

Identify the target platform before designing or coding and follow its guide:

- Web (browser sites and web apps): `platforms/web/` or `/llms-web.txt`.
- Desktop (installed Windows, macOS or Linux apps): `platforms/desktop/` or `/llms-desktop.txt`.
- Mobile (installed iOS or Android apps): `platforms/mobile/` or `/llms-mobile.txt`.

Foundations and tokens are the same everywhere; layout, navigation, input,
component sizing and OS conventions follow the platform guide. A website opened
on a phone follows the web guide.

## Implementation rules

1. Read the relevant docs before coding.
2. Reuse existing tokens and components.
3. Do not invent new core tokens.
4. If a gap exists, propose an extension and document it.
5. Do not replace real content with decorative placeholders.
6. Report deviations and explain why they are needed.

## Output checklist

Before finishing, report:
- target platform (web, desktop or mobile);
- tokens used;
- components/patterns reused;
- responsive or adaptive behavior for that platform;
- accessibility considerations;
- deviations or proposed additions.

# Web

Guía de MXNI para productos que corren en un navegador: sitios de marca,
landing pages, documentación y aplicaciones web. Una aplicación web abierta en
un teléfono también sigue esta guía, usando su layout compacto.

## Tipos de producto web

| Tipo | Prioridad | Expresión MXNI |
|---|---|---|
| Sitio de marca / landing | Historia y conversión | Espaciosa, editorial, composición Bento |
| Documentación | Encontrar y entender | Estructurada, legible, técnica |
| Aplicación web | Completar tareas | Funcional, densidad equilibrada |
| Dashboard | Monitorear y decidir | Densidad equilibrada o compacta, datos primero |

## Páginas de esta guía

1. [Layout y responsive](/platforms/web/layout)
2. [Navegación](/platforms/web/navigation)
3. [Componentes en web](/platforms/web/components)
4. [Interacción y accesibilidad](/platforms/web/interaction)
5. [Checklist de revisión](/platforms/web/checklist)

## Contrato para agentes (web)

Este bloque es suficiente para trabajos pequeños. Para trabajos grandes, lee la
guía completa o `/llms-web.txt`.

**Tokens**

- Fondo `#09070D` (`--mxni-bg`), superficie `#15111C` (`--mxni-surface`),
  elevada `#211A2B` (`--mxni-elevated`), borde `#382C42` (`--mxni-border`).
- Texto `#F7F4FA`, secundario `#B7AABD`, atenuado `#81768A`.
- Marca `#A83FE0`; acentos magenta `#E044C5`, cian `#24CDE0`, lima `#B5F52D`
  (limitado a datos y estados).
- Semánticos: éxito `#39C98A`, advertencia `#F3B64B`, peligro `#F05B72`,
  info `#24CDE0`.
- Manrope para interfaz y títulos; JetBrains Mono para código y metadatos.
- Espaciado `4, 8, 12, 16, 24, 32, 48, 64 px`; radios `2, 6, 10 px` y `999 px`
  solo para pills.
- Movimiento `120 / 180 / 280 / 400 ms`.

**Reglas web**

1. Implementa con los tokens CSS `--mxni-*` de
   [CSS tokens](/implementation/css-tokens); no copies valores sueltos.
2. Diseña mobile-first con los breakpoints Compact `< 640`, Medium
   `640–1023`, Wide `1024–1439` y XL `≥ 1440 px`.
3. HTML semántico: `<a>` para navegar, `<button>` para acciones, encabezados en
   orden y landmarks (`header`, `nav`, `main`, `footer`).
4. Todo funciona con teclado y tiene foco visible (`:focus-visible`).
5. El hover es una mejora; nada depende solo de hover.
6. Objetivos táctiles de al menos `44 × 44 px` en layouts compactos.
7. Respeta `prefers-reduced-motion`.
8. El estado navegable (páginas, filtros, pestañas relevantes) vive en la URL.
9. Objetivo: WCAG 2.2 AA.
10. Reporta tokens usados, comportamiento responsive, accesibilidad y
    desviaciones.

## Qué no hacer

- Forzar un layout de marketing en una aplicación funcional.
- Usar todos los acentos con la misma intensidad.
- Reconstruir el logo con una fuente: usa el [SVG oficial](/brand/logo).
- Poner texto largo en JetBrains Mono.
- Ocultar contenido esencial detrás de hover o de animaciones.

# Web: layout y responsive

## Breakpoints

Usa los breakpoints de [Spacing & layout](/foundations/spacing-layout). Elige
el cambio de layout según el contenido, no según el nombre del dispositivo.

| Nombre | Ancho | Columnas | Margen lateral sugerido |
|---|---:|---|---|
| Compact | `< 640 px` | 4 o una sola columna | `space-4` (16 px) |
| Medium | `640–1023 px` | 4 o 6 | `space-6` (24 px) |
| Wide | `1024–1439 px` | 12 | `space-8` (32 px) |
| XL | `≥ 1440 px` | 12, con ancho máximo | `space-8` (32 px) o más |

**Propuesta:** limita el contenido a un contenedor de entre `1200` y
`1280 px` en Wide y XL para que las líneas y las tarjetas no se estiren.

## Mobile-first

1. Diseña primero el layout Compact en una sola columna.
2. Agrega columnas cuando el contenido lo pida.
3. Mantén el mismo orden de lectura en todos los tamaños; el orden visual no
   debe contradecir el orden del HTML.
4. Nunca debe aparecer scroll horizontal en la página. Las tablas anchas hacen
   scroll dentro de su propio contenedor.

## Densidad por tipo de producto

| Tipo | Densidad | Espaciado entre secciones |
|---|---|---|
| Marca / landing | Espaciosa | `space-12`–`space-16` |
| Documentación | Equilibrada | `space-8`–`space-12` |
| Aplicación web | Equilibrada | `space-6`–`space-8` |
| Dashboard / herramientas de datos | Compacta, nunca apretada | `space-4`–`space-6` |

## Composición Bento

Las composiciones [Bento](/guidelines/bento-composition) funcionan bien en
sitios de marca y dashboards:

- En Wide/XL las tarjetas pueden ocupar varias columnas y alturas distintas.
- En Medium reduce a 2 columnas; en Compact, a una sola.
- Conserva gutters constantes (`space-4` o `space-6`).
- La tarjeta más importante va primero en el orden del HTML.

## Tipografía en web

- Body de `16 px` por defecto; `14 px` solo en interfaces densas.
- Largo de línea de 60–80 caracteres en texto largo.
- Los títulos Display (`48–64 px`) se reducen en Compact (por ejemplo con
  `clamp()`), sin bajar de H1 (`36 px`) en el título principal.
- Carga Manrope y JetBrains Mono preferentemente self-hosted, con
  `font-display: swap`.

## Imágenes y media

- Usa `width` y `height` (o `aspect-ratio`) para evitar saltos de layout.
- Sirve tamaños adecuados con `srcset`/`sizes`.
- Carga diferida (`loading="lazy"`) para imágenes fuera de la primera pantalla.
- El logo siempre es el [SVG oficial](/brand/logo).

# Web: navegación

Aplica los patrones de [Navigation](/components/navigation) con las
convenciones del navegador.

## Estructura

| Patrón | Uso en web |
|---|---|
| Barra superior | Destinos principales del sitio o aplicación, logo y acciones globales (búsqueda, cuenta). |
| Sidebar | Secciones dentro de documentación o aplicaciones con muchas áreas. En Compact se convierte en un panel desplegable. |
| Pestañas | Vistas hermanas dentro de un mismo contexto. |
| Breadcrumbs | Ubicación dentro de jerarquías profundas (documentación, catálogos). |
| Paginación | Listas largas cuando el usuario necesita volver a un punto concreto. |

## Reglas

1. **La URL es parte de la navegación.** Cada página y cada estado que el usuario
   querría compartir o recargar (filtros, pestañas, búsqueda) tiene su propia URL.
2. Los botones "atrás" y "adelante" del navegador deben funcionar.
3. Usa `<a href>` para ir a otro lugar y `<button>` para ejecutar acciones.
4. Marca la ubicación actual visualmente y con `aria-current="page"`.
5. Agrupa la navegación principal en un `<nav>` con nombre accesible.
6. Agrega un enlace "Saltar al contenido" al inicio de la página.
7. Los menús no se abren solo con hover; deben abrirse con clic y teclado.

## Navegación en Compact

- Muestra el logo y un botón de menú con nombre accesible ("Menú") y
  `aria-expanded`.
- El menú abierto atrapa el foco mientras está abierto, se cierra con `Escape`
  y devuelve el foco al botón.
- Mantén visibles las acciones críticas (por ejemplo búsqueda) si caben.

## Logo

- El logo en la barra superior enlaza al inicio.
- Usa el SVG oficial con sus colores originales; respeta la zona libre de
  [Logo](/brand/logo).

# Web: componentes

Los contratos de [Components](/components/overview) aplican igual. Esta página
explica cómo implementarlos en web.

## Botones

- Alturas: `32` (pequeño), `40` (mediano) y `48 px` (grande).
- En Compact, los botones principales usan al menos `44 px` de alto o un área
  táctil equivalente.
- Usa `<button type="button">` o `type="submit"` dentro de formularios.
- Estado de carga: deshabilita el envío duplicado y anuncia el progreso
  (`aria-busy` o texto).
- Radio `radius-md` (6 px).

## Campos

- Usa controles nativos (`<input>`, `<select>`, `<textarea>`) siempre que sea
  posible.
- Cada campo tiene `<label>` visible; el placeholder nunca lo sustituye.
- Usa el `type` y el `autocomplete` correctos (`email`, `tel`,
  `current-password`, etc.); en teléfonos esto abre el teclado adecuado.
- Los errores se asocian al campo con `aria-describedby` y no dependen solo del
  borde rojo.
- En Compact, el texto de los campos debe ser de al menos `16 px`.

## Tarjetas y paneles

- Superficies `--mxni-surface` y `--mxni-elevated`, borde `--mxni-border`.
- Una tarjeta clicable entera usa un enlace con nombre accesible; si tiene
  varias acciones, no hagas clicable toda la tarjeta.
- En Compact, las tarjetas ocupan todo el ancho disponible.

## Feedback

- **Toasts:** en una región `aria-live`; nunca con información esencial.
- **Alertas:** en línea, con título o etiqueta de estado y `role="alert"` solo
  si requieren atención inmediata.
- **Diálogos:** usa `<dialog>` o un patrón equivalente con foco atrapado,
  `Escape` para cerrar y devolución del foco al disparador.
- **Progreso:** `<progress>` o `role="progressbar"` con valor si se conoce.

## Tablas y datos

- Usa `<table>` con encabezados `<th scope>` para datos tabulares.
- En Compact, la tabla hace scroll horizontal dentro de su contenedor o se
  transforma en una lista de tarjetas.
- Números en `font-variant-numeric: tabular-nums`; identificadores y versiones
  en JetBrains Mono.

## Íconos

- Íconos decorativos con `aria-hidden="true"`.
- Botones solo con ícono necesitan `aria-label`.

# Web: interacción y accesibilidad

El objetivo para todo producto web es **WCAG 2.2 AA**. Esta página complementa
[Accessibility](/foundations/accessibility).

## Métodos de entrada

En web no sabes con qué interactúa el usuario: puede ser mouse, teclado,
táctil, lector de pantalla o una combinación. Diseña para todos.

| Entrada | Reglas |
|---|---|
| Teclado | Todo es alcanzable con `Tab`, en orden lógico. Foco visible con `:focus-visible`. Sin trampas de foco fuera de diálogos. |
| Mouse | El hover agrega información o feedback, pero nunca es la única forma de acceder a algo. |
| Táctil | Objetivos de al menos `44 × 44 px`, separación suficiente entre ellos y sin gestos obligatorios sin alternativa. |
| Lector de pantalla | HTML semántico, nombres accesibles, regiones `aria-live` para cambios dinámicos. |

## Foco

- Anillo de foco visible y con contraste suficiente; puedes usar el cian
  `#24CDE0` o el morado `#A83FE0` según el fondo.
- No uses el glow como único indicador de foco.
- Al abrir un diálogo, el foco entra en él; al cerrarlo, regresa al disparador.

## Movimiento

- Duraciones `120 / 180 / 280 / 400 ms` de [Motion](/foundations/motion).
- Con `prefers-reduced-motion: reduce`, elimina o reduce animaciones no
  esenciales.
- Sin parallax que estorbe la lectura y sin destellos.

## Preferencias del usuario

- MXNI es oscuro por defecto. Si el producto ofrece tema claro, guarda la
  elección del usuario y respeta `prefers-color-scheme` como valor inicial.
- Respeta el zoom del navegador hasta 200 % sin perder contenido.
- Soporta `forced-colors` (modo de alto contraste de Windows): los bordes y el
  foco deben seguir visibles.

## Rendimiento

El rendimiento también es experiencia:

- Evita saltos de layout reservando espacio para imágenes y fuentes.
- No bloquees la primera pantalla con animaciones o scripts grandes.
- Muestra estados de carga en operaciones de más de un segundo.

## Validación

- Pruebas automáticas (por ejemplo axe) en cada cambio de UI.
- Recorrido manual con teclado.
- Prueba con un lector de pantalla (NVDA, VoiceOver o TalkBack según el
  público).

# Web: checklist de revisión

Usa esta lista antes de dar por terminada una interfaz web. Los agentes de IA
deben reportar cada punto.

## Marca y tokens

- [ ] Colores, tipografía, espaciado y radios salen de los tokens `--mxni-*`.
- [ ] Los acentos se usan con moderación (5–10 % de la composición).
- [ ] El logo es el SVG oficial con sus colores originales.
- [ ] No hay valores sueltos sin justificar.

## Layout

- [ ] Funciona en Compact (`< 640 px`), Medium, Wide y XL.
- [ ] No hay scroll horizontal en la página.
- [ ] El orden de lectura es el mismo en todos los tamaños.
- [ ] La densidad corresponde al tipo de producto.

## Navegación

- [ ] Cada página o estado compartible tiene URL.
- [ ] "Atrás" y "adelante" del navegador funcionan.
- [ ] La ubicación actual está marcada (`aria-current`).
- [ ] El menú compacto se abre y cierra con teclado y con `Escape`.

## Accesibilidad

- [ ] Todo es operable con teclado y el foco es visible.
- [ ] Encabezados en orden y landmarks presentes.
- [ ] Campos con etiqueta visible y errores asociados.
- [ ] El color nunca es la única señal de estado.
- [ ] Contraste AA verificado en las combinaciones reales.
- [ ] `prefers-reduced-motion` respetado.
- [ ] Objetivos táctiles de `44 × 44 px` en Compact.

## Reporte del agente

- Plataforma: **web**.
- Tokens usados.
- Componentes y patrones reutilizados.
- Comportamiento responsive.
- Consideraciones de accesibilidad.
- Desviaciones o adiciones propuestas.

# Plataformas

MXNI es un solo sistema de diseño: los mismos fundamentos, tokens, componentes y
reglas de marca aplican en todas partes. Lo que cambia entre plataformas es
**cómo** se aplican: el espacio disponible, la forma de interactuar, los patrones
de navegación que el usuario espera y las convenciones del sistema operativo.

Cada plataforma tiene una guía completa y autocontenida. Algunas reglas se
repiten a propósito: así una persona o un agente de IA puede trabajar con una
sola guía sin tener que reconstruir el contexto desde otras páginas.

## Elige la plataforma

| Plataforma | Cuándo aplica | Guía | Para un LLM (fetch) | Para un proyecto local |
|---|---|---|---|---|
| **Web** | Sitios, landing pages, documentación y aplicaciones que corren en un navegador. | [Web](/platforms/web/) | [`/llms-web.txt`](/llms-web.txt) | [Descargar Markdown (.zip)](/downloads/mxni-web-markdown.zip) |
| **Escritorio** | Aplicaciones instaladas en Windows, macOS o Linux (nativas, Electron, Tauri u otras). | [Escritorio](/platforms/desktop/) | [`/llms-desktop.txt`](/llms-desktop.txt) | [Descargar Markdown (.zip)](/downloads/mxni-desktop-markdown.zip) |
| **Móvil** | Aplicaciones para teléfonos y tabletas iOS o Android (nativas o multiplataforma). | [Móvil](/platforms/mobile/) | [`/llms-mobile.txt`](/llms-mobile.txt) | [Descargar Markdown (.zip)](/downloads/mxni-mobile-markdown.zip) |

Si un producto existe en varias plataformas, aplica la guía de cada una a su
versión correspondiente. Una aplicación web abierta en el navegador de un
teléfono sigue la guía **Web** (con su layout compacto); la guía **Móvil** es
para aplicaciones instaladas.

## Qué se comparte siempre

- Paleta de marca, colores semánticos y proporciones de uso ([Color](/foundations/colors)).
- Tipografías Manrope y JetBrains Mono, y la escala tipográfica ([Typography](/foundations/typography)).
- Escala de espaciado `4–64 px` ([Spacing & layout](/foundations/spacing-layout)).
- Radios, bordes, sombras y glow ([Geometry & effects](/foundations/geometry-effects)).
- Duraciones y principios de movimiento ([Motion](/foundations/motion)).
- Requisitos de accesibilidad ([Accessibility](/foundations/accessibility)).
- Contratos y estados de los componentes ([Components](/components/overview)).
- Logo y firma de marca ([Logo](/brand/logo)).

## Qué cambia por plataforma

| Aspecto | Web | Escritorio | Móvil |
|---|---|---|---|
| Entrada principal | Puntero, teclado y táctil | Puntero preciso y teclado | Táctil y gestos |
| Unidad de diseño | CSS px | px del sistema (escalados por el SO) | pt (iOS) / dp (Android) |
| Layout | Responsivo por breakpoints | Ventanas redimensionables | Pantalla completa, orientación y áreas seguras |
| Navegación | URL, barra superior, sidebar, breadcrumbs | Sidebar, pestañas, menús, paleta de comandos | Barra inferior, pilas de navegación, gesto o botón "atrás" |
| Densidad típica | Espaciosa (marketing) o equilibrada (apps) | Equilibrada o compacta | Equilibrada, con objetivos táctiles grandes |
| Tamaño mínimo de control | 44 × 44 px en táctil | 32 px de alto con puntero | 44 pt (iOS) / 48 dp (Android) |
| Hover | Mejora opcional, nunca requisito | Disponible, nunca única vía | No existe |
| Convenciones a respetar | Navegador y estándares web | Sistema operativo (ventanas, menús, atajos) | Guías de iOS y Android |

## Cómo se usa con agentes de IA

Toda la documentación se puede leer aquí y consumir de dos formas.

### 1. En línea: el agente lee la documentación por fetch

1. Identifica la plataforma del trabajo (web, escritorio o móvil).
2. Pide al agente que lea el contexto de esa plataforma:
   `/llms-web.txt`, `/llms-desktop.txt` o `/llms-mobile.txt`. Cada archivo
   incluye las instrucciones para agentes, los fundamentos, los componentes y
   la guía completa de la plataforma en un solo documento.
3. Para trabajos pequeños, basta con el Markdown de la página **Resumen** de la
   plataforma (por ejemplo `/markdown/platforms/web/index.md`), que contiene un
   contrato compacto con los tokens y reglas clave.
4. Cada página de este sitio tiene su Markdown crudo en
   `/markdown/<ruta>.md`; el enlace está al inicio de la página.

Ejemplo de instrucción para el agente:

```text
Antes de escribir UI, lee https://moibaldenegro.github.io/mxvi-design-system/llms-web.txt
y sigue el design system MXNI. Reporta los tokens usados y cualquier desviación.
```

### 2. Local: la documentación vive dentro del proyecto

1. Descarga el `.zip` de la plataforma (tabla de arriba) y descomprímelo en el
   repositorio, por ejemplo en `docs/mxni/`.
2. El paquete incluye un `AGENTS.md` que indica qué leer primero, los Markdown
   del núcleo común y los de la plataforma, y su `llms-<plataforma>.txt`.
3. Referencia la carpeta desde las instrucciones de tu agente (por ejemplo en
   el `AGENTS.md` o `CLAUDE.md` del proyecto):

```text
Para cualquier interfaz, sigue el design system MXNI en docs/mxni/.
Empieza por docs/mxni/AGENTS.md.
```

Los enlaces que empiezan con `/` dentro de los Markdown apuntan a archivos del
paquete: `/foundations/colors` corresponde a `foundations/colors.md`.

Pide siempre al agente que reporte la plataforma usada y cualquier desviación.

## Estado

Las guías de plataforma son una **propuesta v1.0**. Las decisiones marcadas
como **Propuesta** no existían en los fundamentos y deben validarse en
productos reales antes de considerarse estables.

## Semantic colors

Semantic colors communicate meaning, not brand identity. Initial defaults:

| Token | Value | Meaning |
|---|---|---|
| Success | `#39C98A` | Successful operation |
| Warning | `#F3B64B` | Caution or pending |
| Danger | `#F05B72` | Error or destructive action |
| Info | `#24CDE0` | Neutral information |

Do not use lime as the only indicator of success or red as the only indicator of error. Include labels, icons, or text.

## Usage ratios

As a starting point for dark interfaces:

- 65–75% dark backgrounds and surfaces.
- 15–25% neutral text and structural elements.
- 5–10% brand and accent colors.

These are visual heuristics, not strict pixel quotas.

## Contrast

Check text and interactive states against their actual backgrounds. Normal text should target WCAG 2.2 AA contrast (4.5:1); large text and meaningful UI graphics should target at least 3:1 where applicable. Do not assume a brand color is accessible on every surface.

## Rules

- Purple is the primary brand signal.
- Magenta is expressive, not a default action color.
- Cyan highlights interaction and technical information.
- Lime is a limited highlight for data and status.
- Use neutral text for long reading.
- Never use all accents at equal intensity in one composition.

# Typography

## Families

| Role | Family | Usage |
|---|---|---|
| Display / UI | Manrope | Headlines, navigation, labels, interface text |
| Technical | JetBrains Mono | Code, IDs, versions, metadata, technical annotations |

Load fonts locally or from a reliable font provider. For production and privacy-sensitive applications, prefer self-hosted font files with appropriate licensing.

## Type scale

| Token | Size | Weight | Typical use |
|---|---:|---:|---|
| Display | 48–64 px | 700–800 | Campaigns and covers |
| H1 | 36–40 px | 700 | Page title |
| H2 | 28–32 px | 700 | Main section |
| H3 | 20–24 px | 600–700 | Card or subsection |
| Body | 14–16 px | 400–500 | Reading |
| Label | 10–12 px | 600 | Metadata |
| Code | 12–14 px | 400–500 | Code and technical values |

## Rules

- Use sentence case for normal headings.
- Use uppercase sparingly for compact technical labels.
- Keep long-form text in a comfortable line length (roughly 60–80 characters).
- Do not use monospace for paragraphs.
- Do not use ultra-light weights on dark backgrounds.
- Use line height around 1.45–1.7 for body text.
- Typography must remain legible at mobile sizes.

# Spacing and layout

## Spacing scale

| Token | Value |
|---|---:|
| `space-1` | 4 px |
| `space-2` | 8 px |
| `space-3` | 12 px |
| `space-4` | 16 px |
| `space-6` | 24 px |
| `space-8` | 32 px |
| `space-12` | 48 px |
| `space-16` | 64 px |

Use the scale consistently. A one-off value is allowed only when a layout constraint justifies it and should be documented if reused.

## Grid

- Use a 12-column grid for desktop interfaces where useful.
- Use 4 or 6 columns on tablet layouts depending on content.
- Use 4 columns or a single-column flow on narrow mobile layouts.
- Use consistent gutters and alignment.
- Bento compositions may span multiple columns but must preserve a clear reading order.

## Responsive breakpoints

Suggested defaults (adapt to content, not device labels):

| Name | Width |
|---|---:|
| Compact | < 640 px |
| Medium | 640–1023 px |
| Wide | 1024–1439 px |
| XL | >= 1440 px |

## Density

Choose density based on task:
- Marketing/editorial: spacious.
- Dashboards: balanced.
- Data-heavy tools: compact, but never cramped.

Do not make every product use the same density.

# Geometry and effects

## Radius

| Token | Value | Use |
|---|---:|---|
| `radius-sm` | 2 px | Tags, tight controls |
| `radius-md` | 6 px | Inputs, cards, buttons |
| `radius-lg` | 10 px | Large panels and media |
| `radius-pill` | 999 px | Pills only |

MXNI favors controlled corners over overly rounded, playful surfaces.

## Borders

Use `#382C42` for subtle structure on dark surfaces. Borders should clarify grouping without creating a visible grid around every element.

## Shadows

- Use deep black shadows for elevation.
- Use purple glow only for selected or highlighted elements.
- Avoid stacking multiple glow layers.
- Prefer a border or surface change over glow for focus and selection.

## Glow

Recommended starting effect:

```css
box-shadow: 0 0 24px rgb(168 63 224 / 20%);
```

Glow is decorative. It must not be the only indication of focus, selection, or state.

## Gradients

Use localized gradients from purple to magenta. Cyan may appear as a small terminal accent. Avoid broad rainbow gradients.

# Motion

## Principles

Motion should explain state, hierarchy, and cause/effect. It should not delay tasks or distract from content.

## Timing

| Token | Duration | Use |
|---|---:|---|
| Fast | 120 ms | Small feedback |
| Base | 180 ms | Hover and focus transitions |
| Slow | 280 ms | Panels and menus |
| Emphasis | 400 ms | Large, intentional transitions |

Use ease-out for entering elements and ease-in for leaving elements. Avoid spring or bounce effects unless they communicate a meaningful physical interaction.

## Rules

- Provide immediate feedback for actions.
- Do not animate large areas unnecessarily.
- Respect `prefers-reduced-motion`.
- Never use flashing or rapid strobing.
- Avoid parallax that interferes with reading.

# Accessibility

Accessibility is a product requirement, not a visual variant.

## Minimum requirements

- WCAG 2.2 AA is the target for web products.
- Semantic HTML and meaningful heading order.
- Keyboard access for all interactive controls.
- Visible focus state with sufficient contrast.
- Form controls have labels and understandable errors.
- Images have appropriate alternative text.
- Color is never the only way to communicate meaning.
- Motion-sensitive users can reduce non-essential motion.
- Touch targets should be comfortably usable; aim for at least 44 × 44 CSS px where practical.

## Dark UI considerations

Dark interfaces can cause low-contrast text and controls. Test actual combinations; do not rely on visual intuition.

## Focus

Use a clearly visible outline or ring. Do not remove the browser focus indicator without replacing it.

## Validation

Use automated checks (for example axe) and manual keyboard/screen-reader testing. Automated tools do not prove full accessibility.

# Components overview

This section defines the intended contracts for reusable MXNI components. It is a design specification, not yet a published component library.

## Component principles

1. Components consume design tokens.
2. Components expose semantic states.
3. Components support keyboard interaction.
4. Components do not hardcode product-specific brand colors.
5. Variants should solve real use cases, not create arbitrary customization.
6. Composition is preferred over a large number of configuration props.

## State model

Interactive components should consider:

- Default
- Hover
- Focus-visible
- Active / pressed
- Disabled
- Loading
- Error / invalid
- Selected (when applicable)

## Naming

Use clear names such as `Button`, `TextField`, `Card`, `Badge`, `Dialog`, and `Toast`. Keep implementation-specific names out of design documentation unless they are part of the public API.

## Platform adaptation

The contracts on these pages apply to every platform. Sizes, input methods and
OS conventions are adapted in each platform guide:
[Web](/platforms/web/components), [Desktop](/platforms/desktop/components),
[Mobile](/platforms/mobile/components).

## Component maturity

Every component should be marked:
- **Proposed:** documented, not implemented.
- **Experimental:** implemented but API may change.
- **Stable:** reviewed, tested, and safe to reuse.
- **Deprecated:** replacement and removal timeline documented.

# Buttons

## Purpose

Buttons trigger an action. Use links for navigation.

## Variants

| Variant | Purpose |
|---|---|
| Primary | Main action in a context |
| Secondary | Supporting action |
| Ghost | Low-emphasis action |
| Destructive | Irreversible or dangerous action |

## Rules

- Prefer one primary button per action group.
- Label actions with verbs.
- Use a visible focus state.
- Disabled buttons must remain understandable; explain unavailable actions when necessary.
- Loading state must prevent duplicate submission and communicate progress.
- Destructive actions should use explicit language and confirmation when impact is significant.

## Sizing

Suggested heights: small 32 px, medium 40 px, large 48 px. Ensure touch targets remain usable on touch devices.

## Do not

- Use a button only for decoration.
- Use color alone to distinguish destructive actions.
- Place multiple competing primary actions side by side.

# Inputs

## Supported patterns

- Text field
- Password field
- Search field
- Textarea
- Select
- Checkbox
- Radio group
- Switch

## Anatomy

A field should include a label, control, optional hint, and validation message. Placeholder text is not a replacement for a label.

## States

Default, hover, focus-visible, filled, disabled, read-only, invalid, and loading where applicable.

## Rules

- Keep labels persistent.
- Explain format requirements before or beside the field.
- Associate errors programmatically with the control.
- Preserve entered values when validation fails.
- Do not communicate validation only through a red border.
- Use native controls where they provide better accessibility and platform behavior.

# Cards and panels

## Purpose

Cards group related information. Panels provide a larger structural region.

## Surface hierarchy

- Base: `--mxni-bg`
- Surface: `--mxni-surface`
- Elevated: `--mxni-elevated`

## Rules

- Use borders to define structure.
- Use elevation sparingly.
- Avoid nesting cards inside cards without a clear information hierarchy.
- Keep card actions predictable.
- A clickable card must have an accessible name and keyboard behavior.
- Do not make an entire card clickable if it contains multiple independent actions without careful interaction design.

## Bento cards

Bento cards may vary in span and height. Keep consistent gutters, alignment, and responsive order.

# Navigation

## Patterns

- Primary navigation: top-level destinations.
- Sidebar: section-level navigation.
- Tabs: peer views within one context.
- Breadcrumbs: location in a hierarchy.
- Pagination: sequential result sets.

## Rules

- Show the current location clearly.
- Use links for navigation and buttons for actions.
- Preserve logical keyboard order.
- Do not rely on hover-only menus.
- On mobile, provide a clear and accessible navigation disclosure.
- Keep labels concise and recognizable.

# Feedback components

## Toasts

Use for brief, non-blocking feedback. Do not put essential instructions only in a toast.

## Alerts

Use inline alerts for persistent or contextual messages. Include a title or clear status label.

## Dialogs

Use dialogs for focused decisions or tasks. Provide a title, clear actions, keyboard focus management, Escape behavior where appropriate, and a way to close when safe.

## Badges

Use badges for compact metadata and statuses. Pair color with text or icon; avoid using badges as decoration.

## Progress

Show progress for operations with meaningful duration. Use determinate progress only when the amount of work is known.

# Brand identity

## Esencia

**MXNI** es una identidad para un ecosistema de tecnología, software, ingeniería y contenido educativo.

### Propósito

Hacer que los productos y experiencias tecnológicas sean reconocibles, coherentes y claros, sin sacrificar personalidad.

### Personalidad

| Atributo | Significado visual |
|---|---|
| Technical | Precisión, estructura, claridad y detalle |
| Modular | Sistemas, bloques, grids y composición |
| Expressive | Contraste, acentos y personalidad |
| Balanced | Futurismo controlado, no ruido visual |
| Accessible | Jerarquía, legibilidad e interacción clara |

## Principios no negociables

1. La función y legibilidad tienen prioridad sobre la decoración.
2. El color de marca no debe competir con el contenido.
3. Las superficies oscuras crean el lienzo; los acentos crean jerarquía.
4. La composición debe sentirse intencional y modular.
5. Los productos pueden tener personalidad propia sin romper los fundamentos.
6. No utilizar efectos de neón como sustituto de una buena jerarquía visual.

## Tagline

**One identity. Multiple products. A consistent experience.**

## Arquitectura de marca

- **MXNI Web:** sitios, portfolio y landing pages.
- **MXNI Software:** aplicaciones, herramientas y productos SaaS.
- **MXNI Media:** contenido educativo, social y editorial.
- **MXNI Docs:** documentación, conocimiento y recursos técnicos.

Los nombres anteriores son familias de expresión, no necesariamente marcas independientes.

# Visual language

## Dirección

Dark Tech / Modular Bento / Developer Aesthetic.

MXNI debe sentirse como una extensión visual de un entorno de ingeniería moderno: oscuro, preciso, estructurado y expresivo.

## Recursos gráficos

- Grids y líneas técnicas discretas.
- Paneles rectangulares y superficies por capas.
- Geometría abstracta y modular.
- Gradientes localizados entre morado y magenta.
- Cyan para contraste y señales interactivas.
- Lime para datos o highlights puntuales.
- Ruido y texturas con opacidad baja.

## Evitar

- Cyberpunk genérico con exceso de neón.
- Circuitos aleatorios como decoración universal.
- Rojo/naranja como colores dominantes de marca.
- Glow en todos los elementos.
- Gradientes arcoíris.
- Interfaces que parezcan HUD de videojuego sin necesidad funcional.

## Fotografía

La fotografía debe ser auténtica y conservar su jerarquía. No cubrir rostros, manos relevantes ni elementos esenciales con overlays. Corregir exposición y temperatura antes de aplicar efectos.

# Guidelines overview

Guidelines translate foundations into repeatable decisions.

## Composition checklist

- What is the primary task or message?
- What should be noticed first?
- Which elements are structural and which are decorative?
- Is the content readable at its actual size?
- Does the layout adapt to narrow screens?
- Are brand accents used intentionally?
- Can the composition be recognized as MXNI without relying on the logo?

## Content hierarchy

1. Primary message or task.
2. Supporting explanation.
3. Context and metadata.
4. Decorative elements.

Decoration must never outrank the information it supports.

# Bento composition

## Definition

Bento is a modular composition made from rectangular content regions with varied spans. MXNI uses it to express systems, modules, and structured information.

## Rules

- Start with a grid, not arbitrary card placement.
- Establish a clear primary block.
- Use size variation to communicate importance.
- Keep gutters consistent.
- Align edges where possible.
- Maintain a logical reading order in the DOM.
- Reflow modules on smaller screens; do not merely shrink the desktop grid.
- Avoid decorative cards that contain no information or purpose.

## Suggested grid

Desktop: 12 columns. Tablet: 6 columns. Mobile: 4 columns or single column.

## Common failure modes

- Every card has equal visual weight.
- Too many accent colors compete.
- Content is cropped to fit a shape.
- Reading order differs from visual order.
- Layout depends on fixed pixel dimensions.

# Content and data visualization

## Content

- Lead with the information, not the decoration.
- Use concise headings and descriptive labels.
- Keep long-form content readable.
- Use technical labels for context, not as visual noise.
- Maintain consistent terminology across products.

## Data visualization

- Use neutral surfaces and restrained grid lines.
- Reserve accent colors for series or important values.
- Use direct labels when they improve comprehension.
- Do not use 3D effects that distort data.
- Include units, scales, and time ranges.
- Provide a text or tabular alternative when a chart is essential.
- Use color palettes that remain distinguishable for common color-vision deficiencies.

## Semantic colors

Do not use the brand palette as a substitute for a complete categorical data palette. Extend it deliberately and document the mapping.
